# Platform design principles

The cross-cutting rules every platform feature follows. They keep features built at different times, by different people or agents, consistent, coherent, and scalable; a feature that cannot follow one needs a recorded reason, not a silent exception.

1. **The app serves the chain, not the reverse.** On-chain state is the source of truth and the first-class citizen; the app makes it available to people by building and curating a human-level experience over it. This is not a claim that off-chain information is false or irrelevant, but that the app serves the on-chain layer rather than owning a competing reality. [App CMS](./app-cms.md) is a bounded mechanism within that rule: it can curate selected content and suppress or filter how chain-derived items surface, but it does not change the underlying on-chain fact. The account-wide [Permission Viewer](./access-control/permission-viewer.md) derives its display from indexed OSx permission events, while the process-specific view of [scoped authority](./access-control/scoped-authority.md) derives from indexed grants and conditions. The backend indexes events emitted by Aragon accounts, the framework, installed plugins, and relevant associated contracts such as tokens; the frontend reads that derived view through the backend API. The precise event catalogue, indexer topology, service credentials, and third-party API wiring are implementation details unless they change a user-visible product guarantee, so this base does not inventory them.
2. **Product semantics are their own model.** The protocol describes state and state transitions; the product describes the objects and interactions people use to understand and operate it. Concepts such as [process](./governance/process.md), [body](./governance/body.md), and [account](./accounts/account.md) need not map one-to-one to contract storage or mechanisms. A clean correspondence is useful when it exists, never a requirement; use the product vocabulary consistently (the copy rule on [account](./accounts/account.md) is one worked example) and link to the [protocol docs](./protocol-doc/index.md) for mechanics.
3. **Calibrate the abstraction: over-abstract and the product is dishonest; under-abstract and no one can follow.** Expose the user-relevant model, state, and consequences needed for an informed decision, then offer a path to authoritative detail rather than front-loading every implementation distinction. [Honest abstraction](./principles/honest-abstraction.md) carries the rationale, examples, and drill-down boundary.
4. **Accounts are autonomous; the app never restricts them.** An [account](./accounts/account.md) and the [plugins](./governance/plugin.md) holding its permissions are free to act; the app is a convenience layer over supported flows, not the account's gatekeeper. Dangerous supported actions receive a warning, never a block, as with [removing the last known governance process](./accounts/last-process-removal.md). Not supporting every technically possible flow is product scope, not restriction; neither is refusing a configuration that can never hold, such as an unreachable ratio. The account can also reach other applications through means such as [WalletConnect](./governance/action-builder.md#adding-actions), rather than requiring Aragon to rebuild those applications.
5. **The semantic layer sets how far to generalize.** Between one-off implementations and generalizing into meaninglessness, generalize to the semantic layer's object definitions and no further. Prefer reusable components over use-case-specific implementations when they serve the same product meaning, while using judgment about where the shared pattern ends.
6. **Modular over monolithic, because the use cases share one framework.** Token-governed organizations and [Safes](./accounts/safe.md) can share the same product shape: an [account](./accounts/account.md) and governing [bodies](./governance/body.md) that pass [actions](./governance/action.md) to it. Build shared components around that framework so use cases gain shared features and insights instead of isolated interfaces; name the concrete system — plugin, slot, or stage — rather than treating "module" as an abstraction that explains itself.
7. **Isolate the bespoke; each addition is linear.** Keep one-off client-specific logic in [DAO slots](./design/dao-slots.md) and plugin-specific logic in [plugin slots](./design/plugin-slots.md), so it does not spread through generic flows. The aim is for each supported plugin to add bounded, linear complexity; value comes from the plumbing and tooling that let the pieces compose, not from maximizing their number.
8. **Adopt the ecosystem's standards instead of rebuilding them.** Use standards people already expect — [WalletConnect in the action builder](./governance/action-builder.md) and ENS for [Aragon Names](./accounts/aragon-names.md), for example — when they let accounts work with the wider ecosystem without making Aragon recreate another product or host a proprietary substitute. This is practical interoperability, not a promise of seamless interaction.
9. **Aragon is the curator, deliberately and for now.** Aragon currently merges what enters the codebase, hosts the app, reviews code shipped through [DAO slots](./design/dao-slots.md), and builds supported flows around [known plugins](./governance/plugin.md), while unknown plugins remain full citizens of the account. That curation fits a still-small addressable market and Aragon's responsibility for a defensive experience; it may loosen toward more trustless arrangements as the ecosystem matures, without implying a roadmap date.
10. **Every element makes a claim.** A visible interface element says that a concept exists, matters now, or can be acted on. It must earn that claim by serving a reasonable user expectation or current decision; technical possibility and internal architecture alone do not earn representation. See [every element makes a claim](./design/every-element-makes-a-claim.md) and [control availability](./design/control-availability.md).
