# Source repositories

The codebases the platform is built from. The Local path column is relative to the platform-doc repository root (`c:\dev\platform-doc\`), with sibling checkouts under `c:\dev\` and the pinned `protocol-doc/` submodule inside this repository. Inspect first paths are relative to the named checkout.

**Inspect first** names the one file or directory to open before anything else in that checkout: the place that orients a reader on what the repository owns. It is a starting point — see [what each entry point owns](#what-each-entry-point-owns) below for why each was chosen and what a reader should expect around it.

## What each entry point owns

- **`app` → `apps/app/src/plugins/index.ts`.** Names every plugin the app supports and initializes each one's registration, so it is the shortest route to where governance behavior actually lives (see [plugin slots](../design/plugin-slots.md)). The file it feeds, `apps/app/src/initPluginRegistry.ts`, also initializes other extension registries; registry presence alone is not evidence that a feature is live. Two layout facts save a reader time: the frontend is `apps/app`, and the workspace's own hand-written architecture documents have drifted from the code on their plugin and module inventories while the generated ones are current — so where the two disagree, trust the directory listing.
- **`app-backend` → `src/services/aragon-api/routers/v2/index.ts`.** The API surface the frontend actually reads, and its route groups map onto the product's own areas, which makes it the fastest orientation for a backend whose product role is serving derived chain state. The second stop is `src/services/aragon-indexer/configIndexer.ts`, the single best inventory of which onchain events become that state. The repository runs nine deployable services from thin launchers at the repo root over one shared source tree, so it is not nine independent codebases.
- **`gov-ui-kit` → `src/index.ts`.** Two exports that are the whole architecture: brand-agnostic primitives under `src/core`, and governance-domain composites under `src/modules/components`. The [dialog taxonomy](../design/dialog-taxonomy.md)'s two components live in `core`, not modules.
- **`osx` → `src/core/dao/DAO.sol`.** The DAO account itself — the contract that holds assets, executes actions, and stores the permission table every plugin authorizes against; its own documentation names it the framework's entry point. `src/` divides into `common/`, `core/`, and `framework/`. Ignore `packages/`: it holds only a stranded pre-Foundry test suite that no current build references.
- **`crosschain` → `README.md`.** Orients the reader around the controller, executor, CCIP adapter, configuration, fee funding, and two-sided lane wiring, then routes into `specs/SPEC.md` for the function reference and operational runbooks. It describes how to build a deployment, not which account-specific deployments Aragon currently supports.
- **`protocol-doc` → `index.md`.** The upstream bundle's own front door, carrying a start-here reading path and a browse-by-area map over the protocol's concepts, framework, plugins, and helpers. Read-only here.
- **`conditions` → `src/factory/ConditionFactory.sol`.** A short factory that names and deploys the library's complete set of conditions, so it doubles as the inventory: selector allow-listing for `execute()` batches, selector allow-listing for direct calls, and Safe-owner gating.

One caveat when answering component questions from these checkouts: the local `gov-ui-kit` checkout can be ahead of or behind the version a given `app` release builds against. Inspect the UI-kit version locked by the app release and read that tag rather than treating either checkout's current branch as shipped behavior.
