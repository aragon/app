# Basic action details inventory

Scope clarification (owner, 2026-09-13): A17–A18 belong to the BENQI-specific Gauge Registrar integration. The [client scope register](../client-specific-integrations.md) governs product coverage independently of the technical dispatch recorded below.

Evidence for the [basic-action audit](../basic-action-views.md), with the same A01–A22 identities in both inventories. This records source selection and required data; it does not establish deployment availability or successful execution. [Rendering paths, normalization, modes and fallback rules](./rendering-paths.md) apply to every row.

D = proposal details; T = transaction detail dialog; N = ordinary execute/createProposal nested details; X = cross-chain destination children. D/T/N run every plugin normalizer then default normalization and the app registry wrapper. X runs default normalization only and directly renders the UI-kit item. Registered forms never imply detail support. Details dispatch does not require the viewer to hold a picker permission or install the editor component map; the data and registry conditions below determine selection. All these paths are read-only; lower modes use ProposalActionsDecoder (Decoded with inputData, otherwise Raw).

## UI-kit built-ins independently verified

The packaged Basic dispatch has five branches covering eight enum spellings. These are actual component selections, verified in [installed implementation excerpts](./ui-kit-implementation.txt), not inferred from declarations.

| UI-kit runtime type | Component | Action identity / reachable path |
| --- | --- | --- |
| WITHDRAW_TOKEN | ProposalActionWithdrawToken | A01, all detail paths after default normalization. |
| UPDATE_METADATA | ProposalActionUpdateMetadata | A02, all detail paths after default normalization. |
| UPDATE_PLUGIN_METADATA | ProposalActionUpdateMetadata | A03, all detail paths after default normalization. |
| ADD_MEMBERS | ProposalActionChangeMembers | A04 and, incorrectly, A05 after app normalization in D/T/N. |
| REMOVE_MEMBERS | ProposalActionChangeMembers | Built-in exists, but no traced app normalizer emits it. Raw backend MultisigRemoveMembers in X is not this spelling. |
| TOKEN_MINT | ProposalActionTokenMint | A07 in D/T/N after plugin normalization. |
| CHANGE_SETTINGS_MULTISIG | ProposalActionChangeSettings | A06 in D/T/N. |
| CHANGE_SETTINGS_TOKENVOTE | ProposalActionChangeSettings | A08 and A09 in D/T/N with matched plugin metadata. |

An already-normalized UI-kit action supplied to X can select any of these built-ins. That dispatch possibility does not establish that its backend emits those spellings. The matrix describes the traced app/backend spellings. Missing enrichment may produce blank content, an empty state or an exception inside Basic; there is no general downgrade-on-component-error handler.
