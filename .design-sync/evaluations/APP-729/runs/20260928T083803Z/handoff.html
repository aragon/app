1. Supported composition

The member step is a WizardPage.Step containing one AddressesInput.Container and one AddressesInput.Item per row. There is no other supported route: AddressesInput.d.ts exposes only Container and Item (the top-level AddressesInputProps interface is empty), and Item takes no name or value — it addresses its row by index through the container's React context.

// Step lives inside the existing WizardPage.Container. Do not add a form here.
<WizardPage.Step
    id="members"
    order={2}                          // must match the initialSteps entry
    meta={{ name: 'Members' }}         // must match the initialSteps entry
    title="Add your members"
    description="These wallets can create and vote on proposals."
>
    <MembersStepFields />
</WizardPage.Step>

// Row count must track the field array. The container renders children
// positionally against its own useFieldArray fields (see §3).
const MembersStepFields = () => {
    const { fields } = useFieldArray({ name: 'members' });

    return (
        <AddressesInput.Container
            name="members"
            label="Members"
            helpText="Define the wallets that can create and vote on proposals."
        >
            {fields.map((field, index) => (
                <AddressesInput.Item key={field.id} index={index} chainId={chainId} />
            ))}
        </AddressesInput.Container>
    );
};

Prefilling existing members

Seed through the wizard container's own defaultValues. Rows are objects, not strings — the item reads value.address and seeds its local editable string from it, so prefilled addresses appear as text in the input on first render.

<WizardPage.Container
    initialSteps={createDaoSteps}      // includes { id:'members', order:2, meta:{name:'Members'} }
    finalStep="Deploy your DAO"
    submitLabel="Deploy your DAO"
    onSubmit={handleSubmit}
    defaultValues={{
        ...existingDefaults,
        members: existingAddresses.map((address) => ({ address })),
    }}
/>

Per the project README: “AddressesInput rows hydrate from the form default values”, and inside a wizard you “Seed values through the wizard container's own defaultValues instead” of adding a form wrapper.

Row value shape

Written by the item as { address, name } (from onAccept) and appended by the container as { address: '' }. The registered field is the row object at `${fieldName}.[${index}]` — validation and errors sit on the row, not on .address.

3. State ownership — editable string vs. accepted address

This is the part most implementations get wrong, and it is already handled inside Item:

  • The item keeps a local useState string (addressInput), seeded from value.address, wired to AddressInput as value + onChange. That string never reaches the form.
  • onAccept is the only write path into form state: onChange({ address: value?.address, name: value?.name }). So form state holds accepted/resolved values (checksummed address plus resolved ENS name) and nothing in-flight.
  • Consequence per the README: “Do not treat the last accepted value as current while an edit is unresolved”, and onAccept does not emit while ENS requests are loading. A cleared input writes { address: undefined, name: undefined } only once accept fires.
  • An effect re-triggers validation of the row when isAddress(value.address) and the field is dirty or touched. Rows appended programmatically are therefore not validated until interaction or submit.

Do not mirror rows into component state, and do not render the typed text from the form value — read form state for accepted data (review step, submit payload) only.

Distinguishing accepted rows visually

The row renders a Card + AddressInput; there is no “accepted” variant prop in the contract. Any resolved-vs-editing affordance beyond AddressInput's own controls/variants would be new App-side UI. not establishable here — no such design exists in this bundle; treat as a design decision, not a prop. If you add a read-only summary elsewhere (e.g. review step) use AddressOutput, and set hasInteractiveAncestor when the row itself is clickable so it does not add a competing tab stop.

4. Add / edit / remove behavior you inherit

  • Add: secondary button, append({ address: '' }) unless onAddClick is supplied.
  • Remove: per-row tertiary icon button calling the context's onRemoveMember(index). It is disabled whenever fields.length <= 1 — independent of allowEmptyList. With allowEmptyList and one row you cannot reach an empty list via the row button, only via “Clear all”. Flag this to design if an empty list is a required state.
  • More menu (Dropdown, align end) renders only when fields.length > 1: “Reset all” (conditional, see §2) blanks every row's address in place; “Clear all” replaces the array.
  • Keys: the container clones each child with key = fields[index].id. Children past fields.length render null; children fewer than fields.length leave those rows invisible but still in the payload. Hence §1's fields.map.

5. Validation and error reporting

Policy lives in addressesListUtils.validateAddress(address, members, index, customValidator), registered as the row's RHF validate with required: true:

ConditionReturned key
!isAddress(address)app.shared.addressesInput.item.input.error.invalid
duplicate of an earlier row (members.slice(0, index).some(isAddressEqual))app.shared.addressesInput.item.input.error.alreadyInList
customValidator(members[index])your key
  • Duplicates are reported on the later row only; the first occurrence stays clean. Comparison is isAddressEqual, so casing differences still count as duplicates.
  • Errors surface through the App's useFormField hook as the input's critical variant plus an alert, resolved through useTranslations (empty message falls back to app.shared.formField.error.<type>).
  • Because the errors live in the wizard's own form state, the wizard's step gate and submit payload pick them up with no extra wiring. Do not add a parallel validation layer on AddressInput.onChange — the README is explicit that AddressesInput owns required, duplicate and form-level policy.
  • unverified Behavior when an earlier row is still blank: viem's isAddressEqual validates both arguments, and the default add appends { address: '' }. Whether that path throws at the pinned viem version cannot be settled from this bundle — reproduce (prefilled rows + one empty row above a valid one) before shipping.

6. Provider assumptions

  • Form context: supplied by the wizard. Wizard.Root calls useForm and renders FormProvider; WizardPage.Container composes Wizard.Root + Wizard.Form. Nothing extra to add.
  • Copy: DebugContextProvider + TranslationsProvider — required for every key in §5 to render as text.
  • Web3: AddressInput is a modules consumer (wagmi + react-query). In the App this comes from the application provider tree; standalone it needs GukModulesProvider (wagmiConfig, wagmiInitialState, queryClient).
  • Exit guard: BlockNavigationContextProvider backs the wizard's dirty-exit confirmation; omitting it no-ops rather than throws, and it is not required by AddressesInput.
  • not establishable here The actual provider stack at the create-DAO route, and whether the existing wizard already mounts modules/translations providers above the step. Confirm in the App before adding any provider — a second GukModulesProvider or query client at step level is a regression risk.

7. Address, checksum and network semantics

  • Item does not pass enforceChecksum, so the kit default applies: EIP-55 checksum enforcement (the bundle's ChecksumError example shows a broken-checksum mixed-case address flagged on render).
  • Typing can rewrite the string to checksummed form; blur trims whitespace; sanitizeOnBlur: false is set for this field, so no plain-text sanitization runs on the row.
  • ENS resolution is on mainnet regardless of the DAO's target chain. chainId controls explorer links only. Pass the wizard's selected network chain id to Item so links point at the right explorer; do not expect it to redirect name resolution.
  • Accepted values arrive checksummed, and name carries the resolved ENS name when present.

8. Tempting but incorrect choices

  • no Wrapping the step (or the container) in FormWrapper / a second FormProvider. It creates a separate form: inputs write to a context the wizard never reads, so validation gates and the submit payload silently lose members. FormWrapper is for standalone usage only.
  • no Rendering a fixed single <AddressesInput.Item index={0} /> (as in the component's Default example) against a prefilled array. Rows beyond the first never render.
  • no Holding the address list in useState / a step-local reducer and syncing to the form. Row identity, dirty tracking, reset-all and clear-all all run off useFieldArray.
  • no Using AddressInput directly with hand-rolled duplicate/required checks, or adding validation on onChange.
  • no Mounting AddressesInput.Item outside AddressesInput.Container — it reads fieldName and onRemoveMember from the container context.
  • no Storing rows as bare strings (members: ['0x…']), or registering members.0.address yourself. The registered unit is the row object.
  • no Putting the step's controls inside a clickable row or nesting the input in another interactive element; and for any dialog opened from this step, use the controlled open prop (defaultOpen is not a substitute in this bundle) and close(dialogId) rather than bare close().
  • no Reordering existing wizard steps' order values ad hoc. Add the members entry to initialSteps and to the Step props with matching id/order/meta; use disableNext only if you need a gate beyond form validity.
