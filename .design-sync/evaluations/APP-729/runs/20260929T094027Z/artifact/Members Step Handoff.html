2. Supported composition

The member step is AddressesInput.Container holding one AddressesInput.Item per field-array entry, rendered inside the existing WizardPage.Step. No new form wrapper, no new field-array owner, no per-row address component.

// inside the existing create-DAO WizardPage.Container
<WizardPage.Step id="members" order={2} meta={{ name: 'Members' }}
    title="Add members" description="…">
    <MembersField name="members" chainId={chainId} />
</WizardPage.Step>

// MembersField — the only new component
const MembersField = ({ name, chainId }) => {
    // subscribe to the same array so the child count tracks the container's useFieldArray
    const members = useWatch({ name, defaultValue: [] });

    return (
        <AddressesInput.Container
            name={name}
            label={t('…members.label')}
            helpText={t('…members.helpText')}
        >
            {members.map((_, index) => (
                <AddressesInput.Item key={index} index={index} chainId={chainId} />
            ))}
        </AddressesInput.Container>
    );
};

Composition mirrors the shipped Filled example: components/forms/AddressesInput/AddressesInput.prompt.md and _preview/AddressesInput.js → Filled.

Why the parent must subscribe. AddressesInputContainer owns the useFieldArray and then runs Children.map, returning null for any child whose index is >= membersField.length and re-keying the rest with the RHF field id. Children are therefore a caller-supplied list that must track array length: if the parent renders a static number of Items, the container's own Add button appends a row that never renders, and Clear all leaves orphaned children that silently disappear. Watching the same field name is what keeps them in step. verified — _ds_bundle.js → AddressesInputContainer.

4. Initialization from existing members

Row values are objects, not strings. The stored shape per row is { address, name }, where name is the resolved ENS name and may be undefined.

<WizardPage.Container
    defaultValues={{ …existing, members: existingMembers.map((address) => ({ address })) }}
    …
/>
  • Seeding happens through the wizard container's defaultValues. WizardPage.Container accepts defaultValues and composes Wizard.Root, which calls useForm and renders FormProvider.
  • Each item seeds its visible text once, via useState(value.address) at mount. Prefilled rows therefore display correctly on first render.
  • Consequence: a later setValue('members.0', …) updates form state but does not update the text shown in that row's input. If the step must repopulate after mount (for example when a previous step changes the chain or an import runs), remount the affected rows with a changed React key, or replace the whole array and let the keys change. verified
  • An empty starting state is [{ address: '' }], not [], unless allowEmptyList is set.

5. Editable input vs accepted address

Two channels, deliberately separate. Do not collapse them.

ChannelOwnerSemantics
AddressInput.onChangeItem local state (addressInput)Raw editable text. Not untouched input: with enforceChecksum (default true) a valid or all-uppercase address is normalized to checksum form, whitespace is trimmed on blur, and the clear control emits undefined.
AddressInput.onAcceptWritten into RHF as the row valueDebounced, post-resolution { address, name } with a checksummed address and normalized ENS name, or undefined when input is invalid or fails checksum enforcement. Does not emit while an ENS request is in flight.

While an edit is unresolved the form still holds the previously accepted value — never treat the accepted value as "what the user is currently looking at", and never read the raw text back out of form state.

For rows that are displayed rather than edited, use AddressOutput, and set hasInteractiveAncestor whenever the row itself is clickable so it does not add a competing tab stop.

6. Validation and error reporting

Validation is registered by the item through the App's useFormField on `${fieldName}.[${index}]`, so every error surfaces in the owning wizard form's formState.errors and gates the wizard's own navigation and submit. There is no separate error channel to wire up.

RuleTriggerMessage key
requiredRow value missingapp.shared.formField.error.required (generic form-field namespace)
invalidaddressUtils.isAddress(address) false — including the case where a checksum-failing entry was never accepted, so address is undefinedapp.shared.addressesInput.item.input.error.invalid
duplicateAddress equals an earlier row (members.slice(0, index), case-insensitive)app.shared.addressesInput.item.input.error.alreadyInList
customcustomValidator(members[index]) returns a stringCaller-supplied key

Duplicate semantics are asymmetric by design. Only the later occurrence is flagged; the first occurrence stays clean. Do not add a second, symmetric duplicate check on top — you would double-report and fight the field-level policy the container already owns.

  • The item re-triggers validation of its own field when the address is valid and the field is dirty or touched, so reordering/removing rows re-evaluates duplicates for the rows that remain mounted.
  • Error state must be reported through the owning form. Do not lift errors into local state to render your own summary; read formState.errors[name] if the step needs an aggregate message.

Address, checksum and network semantics

  • Input layer is strict. AddressInput.enforceChecksum defaults to true: a mixed-case address failing EIP-55 is rejected at the input and never reaches onAccept.
  • Validation layer is lenient. The App's duplicate/invalid checks use GovKit addressUtils.isAddress, which calls viem isAddress with { strict: false } — case-insensitive, no checksum requirement. isAddressEqual also lowercases and returns false for non-addresses rather than throwing. Net effect: checksum enforcement is the input's job, not the validator's. verified (viem 2.55.19 as bundled)
  • ENS resolution is always mainnet, regardless of the DAO's target chain. chainId only selects the block-explorer network for the row's controls.
  • Accepted output is always checksum-formatted, so the submitted payload needs no further normalization.

8. Tempting but incorrect choices

  1. Wrapping the step in FormWrapper (or a local useForm). The wizard already owns the form. A nested wrapper creates a second, separate context: the inputs write where the wizard never reads, so its validation gates pass and the submit payload silently drops members. Seed through the wizard container's defaultValues instead.
  2. Owning the field array in the step. The container owns useFieldArray — append, remove, replace, and the min-one-row rule. A parallel array controller in the step competes with it. Subscribe read-only (useWatch) for the child count.
  3. Building rows from bare AddressInput. That drops required/duplicate policy, the remove control, the reset/clear menu and the form field registration, and reintroduces the raw-text-vs-accepted bug the item already solves.
  4. Treating the row value as a string. It is { address, name }; defaultValues, custom validators and the submit mapper all see the object.
  5. Mirroring the address into local step state. Accepted values already live in the form; a mirror desynchronizes on checksum normalization, ENS resolution and clear.
  6. Rendering a fixed number of Items — see §2.
  7. Nesting the row inside another interactive element (clickable card, link). It breaks Radix focus order; for read-only address rows use AddressOutput.hasInteractiveAncestor.
  8. Re-implementing add/remove copy. Reuse the existing app.shared.addressesInput.* keys rather than adding step-local strings.
