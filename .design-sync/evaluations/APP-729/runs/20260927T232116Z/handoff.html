1. Scope and what this document is not

The step is built entirely from components already in the bundle: WizardPage.Container/WizardPage.Step (App, group wizards), AddressesInput.Container/AddressesInput.Item (App, group forms), which internally compose the kit's AddressInput. No new input component, no new validation policy, no new form context.

Every contract below was read off the compiled implementation in _ds_bundle.js at the revisions above, or off the generated declarations and selection guide in this project. Anything this project cannot establish is flagged gap in section 10 and must be confirmed against the App repo before implementation.

2. The one supported composition

The wizard owns the form. The step contributes a field array; the addresses container owns the array mutations and the per-row validation policy.

<WizardPage.Container
    defaultValues={{ members: initialMembers }}   /* array hydrates here and only here */
    finalStep="Deploy your DAO"
    initialSteps={createDaoSteps}
    onSubmit={handleSubmit}
    submitLabel="Deploy your DAO"
>
    …other steps…
    <WizardPage.Step
        description="These wallets can create and vote on proposals."
        id="members"
        meta={{ name: 'Members' }}
        order={2}
        title="Add members"
    >
        <MembersField />
    </WizardPage.Step>
</WizardPage.Container>
const MembersField = () => {
    // Same field name the container uses. The container runs its own
    // useFieldArray on this name; this hook only supplies the row count.
    const { fields } = useFieldArray({ name: 'members' });

    return (
        <AddressesInput.Container
            helpText="Define the wallets that can create and vote on proposals."
            label="Members"
            name="members"
        >
            {fields.map((field, index) => (
                <AddressesInput.Item chainId={chainId} index={index} key={field.id} />
            ))}
        </AddressesInput.Container>
    );
};

Child count must track the array length. AddressesInput.Container maps over its children with Children.map, clones each valid child with key = fields[index].id, and returns null for any child at an index >= fields.length. A statically-written list of items therefore renders correctly on first paint and then silently fails to show rows added by the container's own Add button. Deriving children from useFieldArray (or useWatch) on the same name is the only composition that stays correct through add and remove.

Do not render your own add/remove/reset controls beside the container's; they exist and are wired to the container's field array.

5. Editable input vs accepted address

AddressInput exposes two distinct channels, and the item wires them deliberately:

  • onChange(value?: string) — the editable string. The item routes it to local state only. It is not a clean echo of keystrokes: with checksum enforcement a valid or all-uppercase address is normalized to checksum form, surrounding whitespace is trimmed on blur, and the clear/paste controls replace or clear the string (clearing emits undefined).
  • onAccept(value?: IAddressInputResolvedValue) — the resolved result, debounced (recorded as 300 ms) after address/ENS resolution: { address, name } with a checksum address and normalized ENS name, or undefined when the input is invalid or fails checksum enforcement. The item routes this to form state as { address, name }.

Consequences for the step: the committed member value is the accepted one; the visible text may legitimately differ from it mid-edit. onAccept does not emit while an ENS request is in flight, so a last-accepted value must not be treated as current while an edit is unresolved, and the absence of an accept must not be rendered as "invalid". Surfacing accepted state per row, if the step needs it, is read from the form value (address non-empty and addressUtils.isAddress), not from an onChange tap.

Do not re-plumb these callbacks. Passing your own onChange/onAccept into AddressesInput.Item is not part of its contract — its props are index, disabled, customValidator, chainId, plus styling/ref. Reaching for a bare AddressInput to get the callbacks means re-implementing required, duplicate and form-level policy that the App component already owns.

6. Invalid and duplicate reporting through the owning form

The item registers the row with required: true and a validate that delegates to the App's addressesListUtils.validateAddress(address, members, index, customValidator):

  1. !addressUtils.isAddress(address) → error message key app.shared.addressesInput.item.input.error.invalid
  2. duplicate → app.shared.addressesInput.item.input.error.alreadyInList. The check is members.slice(0, index).some(m => addressUtils.isAddressEqual(m.address, address)): case-insensitive, and only earlier rows are compared — the first occurrence stays clean and the later row is flagged.
  3. customValidator(members[index]) → string | true, the extension point for step-specific rules (allow-list, contract-vs-EOA, minimum count per row). Returning a translation key matches how the other two messages are consumed.

Presentation and propagation are already handled: the App's useFormField maps a field error to variant: 'critical' plus an alert whose message is t(error.message) when a validate message exists, otherwise t('app.shared.formField.error.' + error.type) — so the required case resolves to app.shared.formField.error.required with the item's label as the name parameter. The item also re-triggers validation for its own path when the row's address becomes valid and the field is dirty or touched, which is what lets a duplicate resolve or appear as other rows change.

Form-level gating is the wizard's: Wizard.Root calls useForm({ mode: 'onTouched' }), and Wizard.Form submits through handleSubmit(hasNext ? nextStep : onSubmit, invalidHandler) — an invalid member row blocks Next with no extra code, WizardPage.Step renders the step-level critical alert from its own validation status, and the invalid attempt is reported to analytics when the container was given analytics. Use disableNext for a deliberate non-validation block only; it is not the mechanism for invalid input.

Aggregate reads (a count of valid members, a summary on the review step) come from useWatch / formState.errors on the same field name. Error lookups must tolerate the bracket path the item registers; the container normalizes [n] to .n before reading formState.dirtyFields/errors.

7. Address resolution, checksum and network

  • enforceChecksum defaults to true: mixed-case addresses failing strict EIP-55 are rejected, and accepted output is checksum-formatted.
  • ENS resolution is always on mainnet, independently of the DAO's target network. chainId selects the block-explorer network only. Pass the wizard's selected network through AddressesInput.Item chainId so explorer links match the DAO's chain; do not expect it to move ENS resolution.
  • addressUtils: isAddress (forwards options to viem, default strict: false), getChecksum, isAddressEqual (true only when both values are valid addresses, compared case-insensitively), truncateAddress (6 + 4). ensUtils: isEnsName, truncateEns.
  • Read-only renderings of an accepted member (review step, summary rows) use AddressOutput with chainId; inside a clickable row or link set hasInteractiveAncestor so it stops adding a competing tab stop.

8. Provider assumptions

In the App these come from the real provider stack; the assumptions the step depends on are:

  • wagmi + react-query — AddressInput uses wagmi hooks and useQueryClient. In the App this is the application provider stack; in isolation (stories, tests, sandboxes) GukModulesProvider supplies both. There must be exactly one such stack above the wizard.
  • Translations — every App component here calls useTranslations; keys resolve through TranslationsProvider translations={enTranslations}, with DebugContextProvider above it.
  • Navigation blocking — BlockNavigationContextProvider must be above the wizard: the wizard's dirty-state exit confirmation reads that context (it defaults to a no-op context, so a missing provider degrades silently rather than throwing).
  • react-hook-form context — supplied by the wizard. See section 9.

9. Tempting but incorrect choices

Anti-patternWhy it breaks
no Wrapping the step in FormWrapper (or a local useForm + FormProvider) to get form context for the addresses inputThe wizard already owns the form: WizardPage.Container composes Wizard.Root (which calls useForm and renders FormProvider) with Wizard.Form. A nested form context is a second, separate form — the inputs write where the wizard never reads, so its validation gates and submit payload silently lose the members. FormWrapper is for standalone/story use only.
no Seeding members with setValue/reset in an effect inside the stepThe item's editable text is local state seeded at mount; a later write leaves the row visually empty while the form holds a value. Seed through the wizard container's defaultValues.
no Rendering a fixed list of AddressesInput.Item childrenChildren are clipped to the container's field-array length, so added rows never appear; removals leave an orphan child that renders null. Derive children from the array.
no Relying on your own key on itemsThe container overwrites key with the field id. Keying by index elsewhere in your own state will desync from that identity on removal.
no Building the row from a bare AddressInput + local array stateLoses required/duplicate/custom validation, the remove guard, reset/clear actions, the error-to-alert mapping and the re-trigger behavior — and the wizard can no longer gate on the field.
no Treating the onChange string as the member valueIt is edit state: checksum-normalized, blur-trimmed, control-mutated, undefined on clear. The accepted { address, name } is the value.
no Adding a second duplicate check or a symmetric oneDuplicates are already reported, asymmetrically by design (later row flagged). A parallel rule produces double or contradictory messages; extend through customValidator instead.
no Gating Next with disableNext derived from your own validity computationDuplicates the wizard's gate and hides the step-level validation alert. mode: 'onTouched' + handleSubmit already blocks navigation.
no Using chainId to move ENS resolution to the DAO's networkENS resolution is mainnet-only; chainId affects explorer links.
no Wrapping the step in Page.Container for layoutIt requires the App query client. The wizard supplies the page shell; use a plain wrapper if extra layout is needed.
no A nested AddressesInput.Item outside its containerThe item asserts on useAddressesInputContext and throws outside AddressesInput.Container; the container's context also carries the field name and remove handler, so an item cannot be hoisted or reused elsewhere.

10. Not establishable from this project gap

Each of these must be read from the App repo at the recorded revision (or confirmed with the step's owner) before writing code; nothing here was inferred.

  • The real field name and prefix. Whether the create-DAO membership field is members, and whether it sits under a body/stage prefix requiring fieldPrefix, is defined in createDaoForm's definitions, which are not in this bundle. members above is the bundle's example name.
  • The existing wizard's step list — initialSteps, step id/order/meta.name, finalStep, submit labels and whether a membership step already exists under another name.
  • Where the prefilled members come from — the query/hook or route state that produces the initial list, and therefore where checksum normalization belongs.
  • Literal copy. Only translation keys are in this project; the English locale is not. Labels, help text, placeholder and the two error strings resolve at runtime through TranslationsProvider.
  • Submit payload handling of name — whether the resolved ENS name is persisted or dropped downstream of onSubmit.
  • Debounce and resolution internals — 300 ms and the mainnet-ENS rule are recorded in this project's selection guide against the candidate's GovKit revision. Source-to-published-package equivalence for the installed @aragon/gov-ui-kit is recorded as unknown, so verify against the version the App actually installs.
  • Analytics — whether the create-DAO wizard passes analytics, and the flow/prop values to use for the added step's events.
  • Test expectations — the App's co-located tests for addressesInput are not in this bundle; assert through roles, labels and visible text rather than structure.
