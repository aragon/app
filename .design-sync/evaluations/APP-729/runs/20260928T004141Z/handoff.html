1. Supported composition

There is exactly one supported shape for a member list inside a full-page wizard. The wizard owns the form; the container owns the field array and the add/reset/clear actions; each item owns one row's input and its validation registration.

WizardPage.Container   // Wizard.Root (useForm + FormProvider) + Wizard.Form (<form>) + stepper chrome
└─ WizardPage.Step     // registers itself with the wizard stepper; renders only when active
   └─ AddressesInput.Container  name="members"
      └─ AddressesInput.Item index={0..n-1}   // one per entry in the members field array
const createDaoSteps = [
    { id: 'network', order: 0, meta: { name: 'Network' } },
    { id: 'members', order: 1, meta: { name: 'Members' } },
];

const CreateDaoWizard = ({ existingMembers }: { existingMembers: string[] }) => (
    <WizardPage.Container
        finalStep="Deploy your DAO"
        initialSteps={createDaoSteps}
        submitLabel="Deploy your DAO"
        defaultValues={{ members: existingMembers.map((address) => ({ address })) }}
        onSubmit={handleSubmit}
    >
        {/* …other steps… */}
        <WizardPage.Step
            id="members"
            order={1}
            meta={{ name: 'Members' }}
            title="Add members"
            description="These wallets can create and vote on proposals."
        >
            <MembersStepContent chainId={chainId} />
        </WizardPage.Step>
    </WizardPage.Container>
);

// The container does NOT generate rows. It maps its children 1:1 onto the field
// array, so the consumer renders one Item per field entry.
const MembersStepContent = ({ chainId }: { chainId: number }) => {
    const { fields } = useFieldArray({ name: 'members' }); // control comes from the wizard's FormProvider

    return (
        <AddressesInput.Container
            name="members"
            label="Members"
            helpText="Define the wallets that can create and vote on proposals."
        >
            {fields.map((field, index) => (
                <AddressesInput.Item key={field.id} index={index} chainId={chainId} />
            ))}
        </AddressesInput.Container>
    );
};

Row count is driven by the field array, and the container re-keys children itself: cloneElement(child, { key: fieldId, ...child.props }). Children beyond fields.length render null — a hard-coded child list silently truncates or fails to grow when "Add" appends.

4. Editable input vs. accepted address

AddressesInput.Item keeps the editable string in local component state and writes only resolved values into the form:

  • onChange → local addressInput state only. It is not a clean echo of typing: with enforceChecksum (default true) a complete or all-uppercase hex string is rewritten to its EIP-55 checksum on keystroke; blur trims whitespace; the clear control emits undefined; the ENS/0x toggle replaces the string with the other representation.
  • onAccept(value?: IAddressInputResolvedValue) → writes { address, name } into the form field. It emits undefined when the value is invalid or the checksum fails, and does not emit at all while an ENS query is fetching. The last accepted value is therefore stale-by-design during an unresolved edit — never render it as "current".
  • Consequence for the UI: a row that shows text is not a row that has a member. Derive "accepted" from the form value (members[i].address), not from what is on screen.
  • To display accepted members elsewhere (summary/review step), use AddressOutput; inside a clickable row or link set hasInteractiveAncestor so it does not add a competing tab stop.

5. Address resolution, checksum, network

SemanticBehavior in this revision
ChecksumenforceChecksum defaults to true. A valid-but-wrongly-cased address renders a critical alert (kit copy addressInput.checksum) and suppresses acceptance — the form field goes undefined and the form-level "invalid" error follows. AddressesInput.Item exposes no prop to relax this.
ENS resolution chainPinned to mainnet (chainId: mainnet.id internally for both useEnsAddress and useEnsName), independent of the chainId prop.

6. Error reporting through the owning form

Validation is registered by the item on the wizard's form; do not duplicate it.

rules: {
    required: true,
    validate: (member) => addressesListUtils.validateAddress(member.address, members, index, customValidator),
}

// addressesListUtils.validateAddress returns a translation KEY on failure:
//   'app.shared.addressesInput.item.input.error.invalid'       → "Address is not valid."
//   'app.shared.addressesInput.item.input.error.alreadyInList' → "Address has already been added."
// then defers to customValidator?(members[index]) → string | true
  • Duplicates are first-wins: checkIsAlreadyInList compares against members.slice(0, currentIndex), so only the later occurrence is flagged. Comparison is case-insensitive address equality.
  • customValidator runs last — only after the value is a valid, non-duplicate address. Return true or a message/translation key. Use it for product policy (e.g. excluding the DAO's own address), not for re-checking format.
  • Re-validation: the item re-triggers its own field whenever its address changes and the field is dirty or touched. Removing an earlier duplicate does not automatically re-validate the later row; if you need that, call trigger('members') from the step after a removal.
  • Gate: Wizard.Form submits through handleSubmit(hasNext ? nextStep : onSubmit, onInvalid) — Next is blocked by RHF validation over all currently mounted fields, and the footer turns the button critical once isSubmitted and errors exist. Going Back calls clearErrors(). Do not re-implement a gate; WizardPage.Step.disableNext is only for conditions the form does not express.
  • Container-level aggregation is read-only: it walks formState.errors / dirtyFields at the field path to decide whether the "Reset fields" menu action is offered (showResetAllAction, default true). It publishes no error summary of its own — surface list-level messaging (e.g. minimum member count) as your own field/validation on the wizard form.

7. Tempting, and wrong

Wrapping the step in FormWrapper (or any nested <form>)

Wizard.Root already calls useForm and renders FormProvider; Wizard.Form already renders the <form> element. A nested FormWrapper creates a second form context: rows write to a context the wizard never reads, so the Next gate passes on empty data and the submit payload silently omits members. FormWrapper is for standalone/story usage only.

Rendering AddressInput directly for rows

It is the editable-string primitive with no list policy. Required/duplicate/form-level validation lives in AddressesInput.Item; replacing it moves policy into the component tree and drops the translation-keyed errors.

Letting the step own row state

Local useState<string[]> mirrored into the form double-owns the data and fights useFieldArray. The field array is the single source of truth: add via the container's own Add button (or onAddClick when you need a dialog-driven add), remove via the row control, reset/clear via the More menu.

Other traps

  • AddressesInput.Item outside a Container throws: "useAddressesInputContext: the hook must be used within AddressesInputContextProvider".
  • Wrapping items in a layout <div> inside the container breaks the 1:1 child→field mapping (one child, N fields ⇒ one row). Items must be direct children.
  • Index-based props are positional: after a removal, indices shift. Anything keyed by index (locked rows, per-row chainId overrides) must be recomputed from the field array, not memoized by position.
  • Passing enforceChecksum/wagmiConfig/hideControls to Item — not in its prop set; they are dropped.
  • Treating onChange output as user input for analytics or diffing — it is checksum-rewritten and control-mutated.

10. Acceptance checks

  1. Prefilled addresses render one row each, checksummed, with explorer links on the selected chain; no row is in an error state on first paint.
  2. Add appends one empty row; the new row renders (proves the step's row count is array-driven).
  3. Remove is disabled at a single row; the More menu offers Clear all, and Reset fields only once the list is dirty-and-non-empty or in error.
  4. Entering a lowercase-hex address shows the checksum alert and blocks Next; entering an already-listed address flags the later row with "Address has already been added."
  5. Next on an invalid list does not advance and turns the footer button critical; Back clears errors.
  6. Submitting yields members: [{ address, name? }] with checksummed addresses on the wizard's own payload — assert on onSubmit data, not on DOM text.
  7. Assertions use roles, labels and visible text ("Member", placeholder "ENS or 0x…", remove control labelled "Remove member"), not class names.
